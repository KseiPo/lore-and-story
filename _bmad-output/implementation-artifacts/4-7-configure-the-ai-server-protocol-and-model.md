# Story 4.7: Configure the AI server, protocol, and model via a repo file

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the author,
I want to choose my AI server, API protocol, and model from a config file in my synced repo — with only my API key staying in the app's secure Settings,
so that I can use Anthropic directly (with a model of my own choosing), OpenRouter, or a server on my own local network, without ever putting anything secret in a folder that syncs across my devices.

## Context

**FR27 (epics.md, Story 4.7):** the API key must stay exactly where Story 4.1 put it — secure on-device storage, never written to the repo, because the repo is a Syncthing folder that may live on multiple devices. But the AI **server**, **protocol**, and **model** choice are not secret and belong with the rest of this project's repo-versioned config rather than behind an in-app picker screen — the same reasoning Story 4.4 already established for `ai-prompts.md`.

**Not a new file — reuses `lore-story.json`.** Unlike Story 4.4's `ai-prompts.md` (new file, prose content), server/protocol/model/baseUrl is short scalar config, so it fits `lore-story.json`'s existing JSON shape (alongside `loreDir`) better than a new file — a new optional `ai` object, ignored gracefully by every version of the app that predates this story (matching `ProjectConfig`'s own "unrelated keys ignored" forward-compatibility, `project_config.dart:17`).

**Protocol is read-only in this story — Story 4.8 makes it functional.** `protocol: "openai"` is parsed, validated, and stored, but only the existing Anthropic-Messages-format `MessagesApiClient` exists today; no OpenAI-protocol adapter ships in this story. A resolved `server: "openrouter"` or `protocol: "openai"` config will not actually succeed in sending/testing a request until Story 4.8 — that is expected, not a bug to work around here.

**This is the third story to extend `lore-story.json`'s ignored-unless-recognized-key forward-compatibility (after `loreDir`, informally, and now this).** Do **not** merge this into `ProjectConfig` itself (`lore/project_config.dart`) — see Dev Notes "Architecture constraints" for why a second, independent parser of the same file is the correct shape here, not a shared one.

## Acceptance Criteria

1. **(Read the `ai` object)** Given `lore-story.json`'s new optional `ai` object, when the app resolves AI configuration for a send, then it reads `server` (`"anthropic"` / `"openrouter"` / `"custom"`), `protocol` (`"anthropic"` / `"openai"`), `model`, and — for `"custom"` — `baseUrl` from it; the API key is never read from this file, only from Settings' secure storage (`KeyStore`).
2. **(Never blocks, per-field fallback)** Given the `ai` object is absent, invalid, or only partially specified, when the app resolves AI configuration, then it falls back to today's Story 4.1 defaults (Anthropic direct, Anthropic protocol, `claude-opus-4-8`) per missing/unset/unrecognized field — never blocks, mirroring `ProjectConfig`'s own missing/invalid handling (AD-8).
3. **(Custom base URL)** Given `server: "custom"` with a `baseUrl` set, when an AI action sends a request, then it goes to that address instead of the hardcoded Anthropic endpoint.
4. **(Test connection)** Given a resolved server + protocol + model, plus the key from Settings, when I tap "Test connection" (reachable from the Settings screen, next to the key field), then the app makes one minimal live request and reports success or a clear failure reason — without needing a real translate/grammar action just to find out the configuration is wrong.
5. **(Settings unchanged otherwise)** Given the Settings screen, when I open it, then it shows only the API key field (Story 4.1, unchanged) plus the new Test-connection action — no server/protocol/model picker or display lives there; those are configured entirely by editing the repo file.
6. **(No regression for the unconfigured case)** Given the existing Anthropic-direct configuration Story 4.1 shipped (hardcoded model, no repo config at all), when this story ships, then it keeps working completely unchanged for an author who never adds an `ai` object to `lore-story.json`.

**Non-goals** (explicitly out of scope, matching FR27's own text):
- The OpenAI protocol itself is not implemented — `protocol: "openai"` is only read and stored; Story 4.8 makes it functional. Do not build an OpenAI-format request adapter here.
- No in-app editor for the `ai` object — edited with any text editor on the synced repo, same reasoning as Story 4.4.
- No new UI display of the resolved server/protocol/model in Settings (AC5) — Test Connection is an action, not a display.
- Making `server: "openrouter"` actually succeed end-to-end — it won't, until Story 4.8's OpenAI-protocol adapter exists. A honest failure (or an Anthropic-format request against a non-Anthropic endpoint failing) is correct behavior here, not a defect.
- Canceling an in-flight Test Connection request (mirrors Story 4.3's own non-goal for Translate).

## Dev Notes

### What changes, precisely

- **New:** `apps/mobile/lib/ai/ai_server_config.dart` (and its test).
- **Modified:** `ai_client.dart` (two new nullable `AiRequest` fields), `messages_api_client.dart` (`_buildRequest` reads two `?? ` fallbacks — no constructor/field-shape change), `translate_action.dart` + `grammar_action.dart` (one more `resolve*` call each, two more named args on an existing `AiRequest(...)` construction), `ai.dart` (barrel export), `settings_page.dart` (two new constructor params, one new button/handler), `home_page.dart` (`_openSettings` passes two more args).
- **Unchanged:** `lore/project_config.dart` (deliberately — see Architecture constraints below), `key_store.dart`, `context_preview.dart`, `ai_prompt_config.dart`, `main.dart` (the single `aiClient`/`MessagesApiClient` instance built at startup, `main.dart:18`, is never rebuilt or reconstructed — configuration flows in per-request, not by replacing the client), every other page (`editor_page.dart`, `paired_editor_page.dart`, `undetermined_language_page.dart`, `category_entities_page.dart`, etc.) — none of them touch `AiServerConfig` directly; only the two AI-action functions and `SettingsPage` do.

### Architecture constraints

- **AD-8 (never blocks, never throws, degrade-don't-drop):** `AiServerConfig.parse`/`resolveAiServerConfig` must be unconditionally total, exactly like `ProjectConfig.parse`/`AiPromptConfig.parse`. An invalid `server`/`protocol` string degrades that **one field** to `null`, never the whole config (AC2's explicit "per missing/unset field" requirement) — this is a stricter per-field guarantee than `ProjectConfig.parse` itself provides today (its single `loreDir` field falling back means the *whole* config falls back, since there's nothing else to preserve). Do not copy `ProjectConfig.parse`'s "any bad field → return `defaults` wholesale" shape here; copy `AiPromptConfig.parse`'s per-field `flush()` shape instead (`ai_prompt_config.dart:126-142` is the model — this story's version is simpler since it's one flat object, not a multi-section markdown parse, but the "assign only the field that was actually good" discipline is the same).
- **AD-9 (model purity per slice, I/O only in adapters):** `ai_client.dart` (the port) must stay pure Dart — the new `AiRequest.model`/`.baseUrl` fields are plain nullable `String`/`Uri` value fields, no I/O, so this holds trivially. `ai_server_config.dart` performs I/O (`storage.read`) exactly like `ai_prompt_config.dart`/`project_config.dart` already do — this is consistent with those files being adapters-that-parse-config, not violations of AD-9 (which governs the `ai/` slice's *model/matcher* files; config resolvers reading through the `RepoStorage` port are the established pattern here, same as `resolveProjectConfig`/`resolveAiPromptConfig`).
- **AD-12 (barrel discipline, slice internals private):** import `kProjectConfigFile` via `../lore/lore.dart` (the barrel), never `../lore/project_config.dart` directly (Task 1.6). Export the new file from `ai/ai.dart` (Task 6.1) so `app/`-slice code (`settings_page.dart`) never reaches into `ai/ai_server_config.dart` directly. `messages_api_client.dart` stays un-exported, unchanged — its own doc comment's "only `main.dart` and this slice's own tests" rule is untouched by this story.
- **Why NOT extend `ProjectConfig` directly (the most likely wrong turn in this story):** `lore-story.json`'s `ai` object is genuinely an `ai/`-slice concern (it configures `AiClient`/`MessagesApiClient`, consumed only by `ai/` action files and `SettingsPage`) even though it lives in the same *file* `ProjectConfig` (a `lore/`-slice type) also reads. Two independent, single-key-owning parsers of the same JSON text — one in `lore/`, one in `ai/` — keeps each slice's parser simple, keeps `project_config_test.dart`'s 18 existing tests completely untouched (no risk of an `ai`-object bug ever affecting `loreDir` resolution or vice versa), and avoids `lore/` needing to know anything about AI server/protocol/model concepts. This is a deliberate architecture call for this story, not an oversight to "fix" by merging them later.
- **Why the client is reconfigured per-request, not rebuilt per-repo-open:** `main.dart:18` builds exactly one `MessagesApiClient` at app startup, before any repo is even granted — there is no natural "repo opened" moment in the composition root to rebuild it from, and `widget.aiClient` is already threaded as a long-lived, unchanging field through many pages (`home_page.dart:32`, then `editor_page.dart`, `paired_editor_page.dart`, etc.). Rebuilding/replacing that instance would require `HomePage` to hold `AiClient` as mutable `State` and re-propagate a changed reference through every already-open page — a much larger, riskier change than this story's actual job. Resolving `AiServerConfig` fresh **inside each AI action** (mirroring exactly how `AiPromptConfig` is already resolved fresh inside `runTranslate`/`runGrammarReview`, not once at startup) and threading the two resolved values through the existing `AiRequest` object is the minimal, precedent-consistent path — it reuses the *one* client instance for its transport/retry/SSE machinery while still letting per-repo config reach the actual HTTP call.

### Previous story intelligence

Story 4.6 (most recently completed and merged to `main`, done 2026-08-09) and Story 4.4 are the closest precedents:
- Story 4.4 established the "all-nullable fields, per-field `??` fallback, never block" config shape in `ai_prompt_config.dart` — Task 1 of this story is a structural sibling of that file, not of `project_config.dart`. Story 4.6 then proved that shape scales cleanly to a fourth independent field (`grammarInstructions`) with no new logic branch — the same confidence applies to `AiServerConfig`'s four fields.
- Story 4.6's own code review (2026-08-09) surfaced and fixed a config-override footgun worth learning from directly: `# Grammar Instructions` originally could override the ENTIRE system prompt including a machine-readable contract the parser depended on, silently bricking the feature once an author's override omitted that contract. The fix split the two concerns into separate, independently-owned pieces. **This story has an analogous shape to watch for**: `AiServerConfig`'s fields feed into `MessagesApiClient`'s *transport* (URL, model string), not its request *content* — there is no equivalent "override could break parsing" risk here since `model`/`baseUrl` are simple scalars, not free text a parser depends on. Still, keep the same discipline: a resolved value should only ever change *where*/*what model* a request targets, never silently change *what the request contains* in a way another part of the code assumes is fixed.
- Story 4.5 discovered (empirically) that `TabBarView` doesn't eagerly build every tab. Not directly relevant here (this story touches no `TabBarView`), but the general lesson stands: verify assumptions about this codebase's widget lifecycle/state empirically via a test, don't just reason about the tree.
- `deferred-work.md`'s Story 4.3 entry (still open, not required by this story): "`AiAuthException`/etc. are all flattened into one generic SnackBar message... worth a 'No key configured — open Settings' shortcut... once a second real caller of this exception-handling shape exists." Story 4.6 was the second caller (grammar findings) and left it deferred; this story's Test Connection is a **third**, and arguably the most natural place to finally add a "No key configured — go set one" shortcut, since Test Connection already lives on the Settings screen itself. **Not required by this story's ACs** — leave it deferred unless it is essentially free to add while touching `_testConnection`'s error handling; do not silently expand scope. If skipped, it is fine (expected) for this story's own code review to re-flag it as still-deferred.
