# Story 2.18: Assign a language to a bare `.md` file and unlock the translation flow

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the author,
I want to declare which language a file without a language suffix is written in,
so that I can then create the other-language version using the existing translation flow.

## Context

Files with a language suffix (`.ru.md`/`.en.md`) already get RU/EN tabs (Story 2.8) and a "create translation" flow (Story 2.9). But a bare `.md` file — one that predates the bilingual convention, or was never given a suffix — carries no language declaration. The loader already tags such a file `langs['orig']` (see `lore_loader.dart`'s `_buildNode`), but today `entity_detail_page.dart`'s `_openItem` routes an orig-only item (`langs.length == 1 && langs.containsKey('orig')`) straight to the plain single-file `EditorPage` — exactly the "sit as `langs['orig']` with no tabs and no translation path" gap this story closes.

**Scope decision (confirmed with KseiPo, 2026-08-06):** this story targets **sub-entry items only** — the `LoreItem` model, reached via `entity_detail_page.dart`'s `_openItem`. It does **not** extend to top-level simple entities (`LoreEntry`, `category_entities_page.dart`) or section-overview cards (`LoreOverview`), because neither carries any `langs`/base-filename-pairing concept in the current loader — extending to them would mean adding a new pairing mechanism to the loader itself, a model/golden-fixture-contract change (touching the JS reference too) that epics.md's own dependency list for this story (only Stories 2.8/2.9) gives no indication was intended. Scoping to `LoreItem`s needs **zero loader/model changes** — the `langs['orig']` data this story consumes already exists.

This scope choice also happens to make AC6 (entity-folder cards excluded) automatically true **by construction**, with no extra guard code: `_buildNode`'s pairing loop already diverts any bare file whose base matches its own parent folder's name into becoming a `LoreOverview` (`if (base == dirName || base == 'index') { ... continue; }`) — such a file can **never** become a `LoreItem` in the first place. Verified by reading `lore_loader.dart` before writing this story.

**A second, unplanned simplification:** epics.md's own notes for this story flagged "`RepoStorage` may need a `rename` method (or read+writeAtomic+delete)." Story 2.17 (done, merged) already added exactly that — `RepoStorage.movePath(from, to)`, a single atomic filesystem rename, byte-exact by construction (no content re-encode). This story reuses it verbatim for a **same-directory** rename (`events/foo.md` → `events/foo.ru.md`) — simpler than Story 2.17's cross-directory promotion, since the destination's parent directory is already the source's own directory (no `ensureDir` call needed at all). **Zero changes to `repo_storage.dart` / `all_files_repo_storage.dart` / the `movePath` parts of `test/fakes.dart` are needed or in scope** — this story is UI-layer only.

## Acceptance Criteria

1. **(extends FR12)** Given a sub-entry item whose only language variant is `orig` (`item.langs.length == 1 && item.langs.containsKey('orig')`), when I open it, then a screen shows the **usual `[RU][EN]` tabs, same as a known-language pair** — but **neither is marked active** (the language genuinely isn't known yet). The body is the real file — I can read (and edit) it immediately, exactly like any other file; nothing about viewing or editing it is gated behind declaring a language. *(Corrected 2026-08-06 after KseiPo caught the first draft: it showed two inert "choice" buttons with no visible document at all, forcing a blind decision before the content could even be read — the opposite of the intent.)*
2. **(extends FR13)** Given the undetermined tabs, when I tap either one (e.g. "RU"), then a confirmation dialog appears: "Is this file written in Russian?" (or "...English?" for EN). Tapping a tab **only ever asks** — it never gates or changes what's already visible (there's one real file regardless of which tab is tapped).
3. **(extends FR12/FR13)** Given I confirm the language choice, when the confirmation succeeds, then any unsaved edit is saved first (never rename a file out from under a dirty buffer — AD-10), the file is renamed from `<slug>.md` to `<slug>.<lang>.md` (e.g. `first-meeting.md` → `first-meeting.ru.md`) via `RepoStorage.movePath` (same directory, no `ensureDir` needed), and the screen transitions **in place** (no pop/re-navigate) to the standard paired-editor state: the confirmed language's tab is active with the file's (possibly just-edited) content, the other tab shows Story 2.9's "create translation" flow (an empty tab that creates the file on first save).
4. Given I cancel the confirmation dialog, when I dismiss it, then nothing changes — the file stays as bare `.md`, any unsaved edit is preserved untouched (not saved, not discarded), and the screen remains in the undetermined state.
5. **(AD-8/NFR7)** Given any failure during the rename (permission error, disk full, a same-named file already at the target) — or a buffer that's dirty but cannot be safely saved (a lossy load) — when it happens, then a snackbar shows the error, the file stays as `.md` (never partially renamed — `movePath` either fully succeeds or leaves the source untouched), and the screen is not stranded — it's still usable, still showing the undetermined tabs and the editable content.
6. Given an entity-folder card (`<slug>/<slug>.md`) or a section-overview card, when it opens, then no language-choice screen is shown — unaffected by this story, since neither is ever a `LoreItem` (verified true by construction, not a new guard).

**Non-goals (explicitly out of scope):** top-level simple entities and section overviews (see Scope decision above — a hypothetical future story, would need a loader/model change); demoting/un-declaring a language once set (no such feature exists or is requested); the multi-variant collision case where a base name already has both `orig` **and** `ru`/`en` siblings (`langs.length >= 2`) — this already routes to the existing `PairedEditorPage` today (which already labels an `orig` tab "Original"), unaffected by this story.

### Architecture constraints

- **AD-3/AD-9** (all filesystem access through `RepoStorage`, I/O isolated to adapters): this story calls only `RepoStorage.exists`/`movePath`, both already-existing port methods — no new port surface, no `dart:io` anywhere in `app/`.
- **AD-4/NFR1** (atomic, byte-exact): `movePath` is a single filesystem rename — no content re-encode, so this holds by construction, same reasoning as Story 2.17.
- **AD-6** (RU/EN pairs are a view; saves target the individual file): once delegated to `PairedEditorPage`, this is entirely `PairedEditorPage`'s existing, already-tested responsibility — nothing new to reason about here.
- **AD-8/NFR7** (total, never crash, never strand): every failure mode (existing target, I/O error) must leave the screen in the undetermined state, usable, with a clear snackbar — never a blank/frozen screen.
- **AD-10** (model rebuilt, not patched): the in-place `setState`-driven `_item` swap after a successful rename is a **local, single-widget** state transition, not a claim about the app-wide model — the reconstructed `LoreItem` only exists to hand off to `PairedEditorPage` within this same screen instance; the *actual* model is still rebuilt via `_rescan()` back in `entity_detail_page.dart` once this screen is eventually popped, exactly like every other authoring op in this app. Don't read this local reconstruction as a precedent for patching the shared model elsewhere.

### Previous story intelligence

**Immediate previous story (2.17, done, merged to main as `8a00ce3`):** the direct source of `RepoStorage.movePath`, reused verbatim here — read that story's Dev Notes for `movePath`'s exact contract (`RepoStorageException` if source is missing or the OS rename fails; caller must check `exists` on the target first; caller must `ensureDir` first **only** when the destination is in a different, possibly-new directory — not needed here, same directory). 2.17's own code-review cycle is also worth knowing: its first cut over-guarded (checking both the target folder and file's existence before a cross-directory move), which turned one transient failure into a permanently-unrecoverable state; this story's guard is simpler (same-directory, `exists(newPath)` only, no `ensureDir`-orphan risk exists here at all since there's no folder-creation step). 2.17 also added `FakeRepoStorage.failMove` specifically so a sibling story could test a `movePath`-failure path without adding new fake capability — **reuse it directly** (Task 3.1) rather than adding a second failure-injection flag.
