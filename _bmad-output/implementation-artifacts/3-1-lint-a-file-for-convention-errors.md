# Story 3.1: Lint a file for convention errors

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the author,
I want a navigable list of styling mistakes in a file,
so that I can clean it up quickly.

## Context

This is the first Epic 3 story — the start of "convention tooling (v0.2)." Story 2.5 built the convention **highlighter** (`convention_matcher.dart` + `ConventionHighlightingController`), and Story 2.6 extended it with **error kinds** (`leakedTwee`, `leakedHtml`, `malformedMarkup`) for suspect/invalid markup, explicitly deferring two things to this story (see `convention_matcher.dart`'s own doc comments): **"unpaired conditionals, dangling wikilinks"** and the note that `malformedMarkup` is deliberately scoped to just the unterminated-`[[` case, "broader malformed detection... is the Story 3.1 linter."

**FR18 (the authoritative source — more precise than epics.md's compressed summary), from `prd.md`:**
> A convention linter flags mechanically detectable styling errors using the same matcher as FR9/FR9a's highlighter: leaked twee markup (`<<`, `>>`, HTML), `<<=$var>>` where a `[placeholder]` belongs, Twine passage-link syntax in scene files (`[[label->passage]]` / `[[a|b]]` where `**label** _(→ target)_` belongs), dialogue lines missing the `Name:` shape, unpaired em-dash conditional markers, and `[[wikilinks]]` pointing at entities that don't exist. Offline, no AI.

**Two things resolved before writing this story (both verified by reading code, not assumed):**

1. **The "Twine passage-link syntax... where the bold form belongs" item is stale — do NOT implement it.** FR9a/FR18 were written 2026-07-19, before Story 2.15 (2026-08-05) made `[[label->passage]]`/`[[a|b]]` the **new canonical, valid** scene-navigation-link syntax, explicitly **superseding** the old bold-form convention this FR text describes (`ARCHITECTURE.md`: *"A `[[...]]` pair with a separator... is a scene-navigation link instead (2026-08-05)"*). The matcher already reflects this correctly: `sceneLink` is a **valid** kind, not in `errorKinds`. **Do not add any detection that flags a `sceneLink` token as an error** — that would contradict Story 2.15's shipped, tested convention. This item of FR18 is obsolete and out of scope.
2. **Dangling-wikilink detection (needs the loaded entity list) is IN scope, not deferred.** Originally scoped out for this story (needs the entity title/alias set, which the editor doesn't currently have access to), then brought back in after checking the actual blast radius: `loreDir` is **already** a field on every page that opens `EditorPage`/`PairedEditorPage` (`HomePage`, `CategoryEntitiesPage`, `EntityDetailPage`, `ConflictsPage` all already carry it) — only `EditorPage`/`PairedEditorPage` themselves don't accept it yet. Adding it is a small, mechanical pass-through at ~6 call sites, not a wide refactor. Doing it now also means **Story 3.2** (autocomplete + navigate, FR19 — which needs the same entity-list access) doesn't have to repeat this plumbing.

**No new "parse entities" work is needed** — `loadLore` (Story 2.1a/2.1b) already returns `LoreModel.entries`, and every `LoreEntry` already carries `.title` + `.aliases`. This story only exposes that already-computed data to the editor.

## Acceptance Criteria

1. **(FR18 — leaked twee/HTML, extends Story 2.6)** Given a file containing `leakedTwee` or `leakedHtml` tokens (the matcher's existing detection, unchanged), when I open the lint panel, then each occurrence is listed as a finding with its line number and a short description.
2. **(FR18 — malformed dialogue, NEW matcher detection)** Given a line with a dialogue-speaker-shaped prefix (same shape `_dialogue` already recognizes) followed by a colon with **no space and not at end-of-line** (e.g. `Frank:hello`) — the exact way a dialogue line breaks when the required space is missing — when the matcher runs, then it's tokenized as a new `ConventionKind.malformedDialogue` error kind, styled by the highlighter (free, same matcher) and listed by the linter. This is a narrow, conservative pattern chosen specifically to avoid amplifying the `_dialogue` heuristic's existing false-positive surface (ordinary prose with an early colon already partially matches `_dialogue`, documented in `2-5-...md`'s deferred items) — do not broaden it to "any line that looks like it might be dialogue."
3. **(FR18 — unpaired em-dash conditional markers, NEW matcher detection)** Given the authoring convention from `ARCHITECTURE.md` (`— если <condition> — … — иначе — … — конец условия —`), when a file has an opening `— если …` marker with no matching `— конец условия —` before EOF or the next `— если …` (or vice versa — a stray `— конец условия —` with no preceding open), then each unpaired marker is tokenized as `ConventionKind.unpairedConditional` and listed as a finding (case-insensitive match on `если`/`конец условия`; `— иначе —` is not itself checked for pairing, only that `если`/`конец условия` balance). This is inherently cross-line (unlike every other matcher check, which is per-line) — see Dev Notes for the suggested implementation shape.
4. **(FR18 — dangling wikilinks)** Given a `wikilink` token (never a `sceneLink` — see Context #1) whose bracketed text does not case-insensitively exact-match any loaded entity's title or alias, when the lint panel runs, then it's listed as a finding. When the entity list couldn't be loaded (I/O failure — AD-8), this check is silently skipped (no false "everything is dangling" findings) rather than erroring the whole panel.
5. **(Navigation)** Given a finding, when I tap it, then the editor jumps to that line — switching out of preview if needed (the raw text must be visible to edit) and placing the caret at the start of that line.
6. **(Offline, NFR4/NFR6)** Linting never makes a network call and never blocks the UI noticeably (NFR6 — "instant"); it's the same local matcher plus one local `loadLore` walk (already an established, fast operation — see Story 2.1b).
7. **(AD-8 — never crash)** A file with zero findings shows a clear "No issues found" state, not an empty/broken panel. A `loadLore` failure while gathering the entity list degrades to "syntax-only findings" per AC4, never a crash or a blocked panel.

**Non-goals:** `<<=$var>>`-in-place-of-`[placeholder]` is **not** a separate detector — it's already caught by the existing `leakedTwee` pattern (`<<...>>` matches regardless of what's inside), so AC1 covers it with zero new code. No autocomplete, no wikilink navigation-on-tap in preview (that's Story 3.2, FR19 — this story only adds the `loreDir` plumbing Story 3.2 will also need). No AI. No changes to `lore_loader.dart`, `lore_model.dart`, or any golden fixture — the entity list this story reads is already fully computed by the existing loader.

## Dev Notes

### What changes, precisely

- **New files:** `apps/mobile/lib/lore/convention_lint.dart`, `apps/mobile/lib/app/lint_panel.dart`, plus their test files.
- **Modified:** `convention_matcher.dart` (2 new `ConventionKind`s + detection), `file_editor.dart` (+`text` getter, +`jumpToLine`), `editor_page.dart` + `paired_editor_page.dart` (+`loreDir` field, +Lint AppBar action), and every call site of those two widgets (mechanical `loreDir:` argument addition).
- **Unchanged:** `lore_loader.dart`, `lore_model.dart`, `repo_storage.dart`/`all_files_repo_storage.dart`, `undetermined_language_page.dart`'s own constructor (already has `loreDir`) — though it gains its own Lint AppBar action per Task 5.2.

### Architecture constraints

- **AD-7 (one matcher, many consumers):** both new error kinds live in `convention_matcher.dart`, not in a linter-only side-channel — so the highlighter styles them for free (Story 2.5's existing surface), exactly matching this file's own doc comment and MOBILE.md §6.1's "build once, surface twice."
- **AD-9 (per-slice purity):** `convention_lint.dart` must stay pure Dart — no Flutter, no `dart:io`. It takes plain strings/sets in, returns plain data out. All I/O (`loadLore`) happens in the UI layer (`lint_panel.dart` / the hosting pages), which then hands `lintText` its inputs.
- **AD-8 (total, never crash):** both `matchConventions` and `lintText` must never throw; a `loadLore` failure during Task 5.3 degrades gracefully (empty `knownEntityNames`, syntax-only findings), never blocks or crashes the panel.
- **AD-10 (rebuild, not patch):** the entity-name set for dangling-wikilink checking is loaded **fresh** via `loadLore` each time the panel opens — no caching, no threading a whole `LoreModel` down through widget constructors. This matches every other page's existing rescan-on-demand pattern (`_rescan()` in `entity_detail_page.dart`/`category_entities_page.dart`) rather than introducing a new stale-cache risk.
- **Testing standard for this story specifically:** `convention_matcher.dart` and `convention_lint.dart` are pure business logic — cover them thoroughly (every new kind, every edge case named in the ACs). The UI wiring (Task 5) is exactly the kind of thing this project's testing philosophy says not to over-test — one or two representative end-to-end flow tests are enough; don't write a widget test for every finding kind rendering correctly in the panel, that's already proven by Task 2's pure tests.

### Previous story intelligence

Stories 2.18/2.19 (most recently completed, both code-reviewed) surfaced two recurring lessons directly relevant here:
- **Verify a "should work" claim against the actual downstream consumer, don't trust inspection alone.** Story 2.18's review caught a real bug in a symmetric-looking code path that turned out asymmetric; Story 2.19's review caught a chip that silently wrote to the wrong folder because two code paths (display text vs. write target) diverged. This story has a similar shape risk in Task 1.3 (the cross-line conditional-marker check) and Task 2.2 (line-number computation from byte offsets) — **write the test in 1.4/2.3 that proves the exact `ARCHITECTURE.md` example round-trips correctly**, don't just eyeball the regex.
- **When a written spec (FR/AC) contradicts already-shipped, tested behavior, that's a real conflict to resolve explicitly, not silently interpret.** This story's Context section already did that resolution work (the stale `sceneLink`-as-error item) — the reasoning is recorded there so it doesn't need re-litigating during implementation.

- Task 1 surfaced two real bugs caught by tests, not assumed away:
  - `_malformedDialogue`'s first draft flagged `'>:( face'` (an emoticon) as malformed dialogue — an existing FR9a regression-guard test caught it immediately. Fixed by requiring a minimum 2-character prefix (`{1,39}?` → `{1,39}?` was already there for the body; the fix was excluding a 1-character-only prefix from ever reaching the colon check), so a single punctuation symbol can never look like a speaker name.
  - `_condOpen`'s first draft used `\b` after "если" (`—\s*если\b…`) — this silently failed to match on every single test case. Root cause: Dart's `\b` is defined in terms of ASCII `\w`, so it never anchors correctly immediately after Cyrillic text. Fixed by removing `\b` entirely; the `—\s*` prefix is specific enough on its own.
  - One pre-existing Story 2.5 placeholder test (`'em-dash conditional marker'`, asserting `'— если —'` produces two generic `emDash` tokens) needed updating — it was written before conditional-marker detection existed and documented the *absence* of the feature Story 3.1 delivers. Updated to assert the new, correct behavior (a single unpaired-conditional finding) with a comment explaining why, mirroring how Story 2.19 handled its own intentionally-superseded test.
  - The cross-line conditional-marker tokens can overlap per-line tokens (e.g. `**bold**` inside a condition clause) — the first design assumed no overlap was possible (wrong) and just re-sorted; fixed by removing (not clipping) any per-line token a marker's span overlaps before merging, preserving `matchConventions`'s non-overlapping guarantee.
