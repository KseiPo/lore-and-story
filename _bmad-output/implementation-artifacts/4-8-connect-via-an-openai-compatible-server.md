# Story 4.8: Connect via an OpenAI-compatible server

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the author,
I want the app to be able to speak the OpenAI chat-completions protocol,
so that I can use OpenRouter, or a local OpenAI-compatible server such as LM Studio, as my AI provider.

## Context

**FR28 (epics.md, Story 4.8):** implement an OpenAI-compatible chat-completions client (streamed, with the same typed-error/retry discipline as the Story 4.1 Anthropic client) as a second protocol adapter, so the app can talk to OpenAI-protocol servers — OpenRouter, or a self-hosted local server such as LM Studio.

**Story 4.7 built the config, deliberately left it inert for this case.** `AiServerConfig`/`resolveAiServerConfig` (`ai/ai_server_config.dart`) already parse `server` (`anthropic`/`openrouter`/`custom`), `protocol` (`anthropic`/`openai`), `model`, `baseUrl` from `lore-story.json`'s `ai` object. But only the Anthropic-Messages-format `MessagesApiClient` exists — `resolveCustomOrigin` (the function that turns a resolved config into the `Uri?` a request should target) **throws `AiConfigException` for `server: "openrouter"`** ("not yet supported by this version of the app") and `protocol: "openai"` is parsed and stored but never acted on. This story is exactly the "Story 4.8 makes it functional" this codebase's comments already promise in several places (`ai_server_config.dart:179`, `ai_client.dart:100`, the 4.7 story file's own Non-goals).

**Two real destinations, one shared port.** "OpenAI protocol" in this story covers two distinct real-world targets with different needs:
- **OpenRouter** (`server: "openrouter"`) — a real cloud API at a fixed, app-known endpoint (`https://openrouter.ai/api/v1`), always needs a key (from Settings' secure storage, same as Anthropic), and — per FR28's own AC — defaults its protocol to `openai` when unset, since that's the only protocol it speaks.
- **A custom local server** (`server: "custom"` + `protocol: "openai"` + `baseUrl`, e.g. LM Studio on the author's LAN) — an address the author supplies, and per this story's own AC, **the key is optional** — a local server on the LAN typically doesn't require one.

**Test Connection's key-gating has to change, and 4.7 said so explicitly.** The 4.7 story's `deferred-work.md` entry (`4-7-configure-the-ai-server-protocol-and-model`, still open) says outright: *"Story 4.8's own AC states a local OpenAI-compatible server needs no API key at all... which forces that story to revisit this gating regardless."* Today `SettingsPage`'s Test Connection button only renders in the `_Stage.configured` case (a key must already be saved). This story has to also surface it when no key is saved, so a key-less local server can be tested at all (AC3).

## Acceptance Criteria

1. **(OpenAI-format request/response)** Given API Protocol resolves to OpenAI (explicit `protocol: "openai"`, or `server: "openrouter"` with `protocol` unset — see AC2), when an AI action sends a request, then it is built and streamed per the OpenAI chat-completions format — `Authorization: Bearer <key>` (only when a key is configured; see AC3), a `messages` array with `system`/`user` roles (not Anthropic's separate top-level `system` field), `delta.content` streaming chunks, and a `data: [DONE]` sentinel ending the stream — rather than the Anthropic Messages format. Every downstream feature (translate, grammar, Test Connection) works unchanged against either protocol — none of `translate_action.dart`/`grammar_action.dart`'s own logic branches on protocol; only the resolved `AiRequest` and which `AiClient` it's routed to differ. *(FR28)*
2. **(OpenRouter defaults to OpenAI)** Given `server: "openrouter"` in `lore-story.json`'s `ai` object (Story 4.7), when `protocol` is left unset, then it defaults to OpenAI (the only protocol OpenRouter speaks) and the request goes to OpenRouter's fixed endpoint (`https://openrouter.ai/api/v1/chat/completions`); the OpenRouter API key itself still comes only from Settings' secure storage, never from the repo file.
3. **(Optional key for a local server)** Given a Custom local address configured with the OpenAI protocol (e.g. LM Studio's OpenAI-compatible endpoint), when I tap Test Connection, then it succeeds against a real local server, with the API key field optional — Test Connection is reachable (and a request can be sent with no `Authorization` header at all) even when no key has been saved yet, not only from the `configured` stage.
4. **(Same failure classes, same retry discipline)** Given the same failure classes Story 4.1 defined for the Anthropic client (auth, invalid request, rate limit, server error, network failure, timeout), when using the OpenAI protocol, then equivalent typed errors (`AiAuthException`/`AiInvalidRequestException`/`AiRateLimitException`/`AiServerException`/`AiNetworkException`) and the same retry/backoff discipline apply — one shared `AiClient` port, two protocol adapters behind it, both built on the same retry/backoff/timeout machinery so a fix to one automatically benefits the other. (Deliberate, in-scope divergence: unlike Anthropic, a missing key never throws `AiNotConfiguredException` for the OpenAI protocol — AC3 requires it to be optional. `AiNotConfiguredException` is not one of the failure classes this AC lists, and this divergence is the whole point of AC3.)

**Non-goals** (explicitly out of scope):
- No OpenAI-native "tool calling"/function-calling support — only plain text streaming, matching what `AiRequest`/`AiClient` already model for the Anthropic adapter.
- No `thinking`/extended-reasoning equivalent for the OpenAI protocol — that's an Anthropic-specific request field (`messages_api_client.dart`'s hardcoded `thinking: {type: 'adaptive'}`); the OpenAI adapter's request body has no equivalent field.
- No provider-specific extra headers (e.g. OpenRouter's optional `HTTP-Referer`/`X-Title` attribution headers) — not required by any AC; a plain `chat/completions` request works against OpenRouter without them.
- No UI display of which protocol/server is currently resolved anywhere outside the existing context-preview "Server" section and the Settings warning banner (both already shipped in Story 4.7 unchanged) — Settings still shows no server/protocol/model picker (Story 4.7 AC5, unchanged by this story).
- No "test the key I just typed but haven't saved yet" flow — Test Connection (in the newly-reachable `notConfigured` stage) tests against whatever `KeyStore` currently holds, i.e. no key, which is exactly the local-server AC3 case. Testing an unsaved key is a different feature, not asked for here.
- No change to how `server: "custom"` + `protocol` left unset (or explicitly `"anthropic"`) behaves — that already works today (a custom Anthropic-compatible endpoint) and is untouched by this story.
- No special detection of the reverse inconsistent combo — `server: "openrouter"` with an **explicit** `protocol: "anthropic"` (the mirror of the `server: "anthropic"` + `protocol: "openai"` case Task 4.4 *does* reject). That one is deliberately left unhandled: the request still reaches a real, correct endpoint (OpenRouter) in the explicitly-requested wire shape, and fails there naturally and loudly (an auth/format rejection from OpenRouter) rather than being silently misrouted — so it doesn't trip the "never silently send to the wrong place" guard the other checks exist for. Not worth a third special case for a config an author would have to write against the documented default.

    - Constructor: `required http.Client httpClient`, `int maxAttempts = 3`, `Duration Function(int attempt)? backoff`, `Duration requestTimeout = const Duration(seconds: 30)`, `Duration streamIdleTimeout = const Duration(seconds: 60)` — same defaults, same shape as `MessagesApiClient`'s own constructor params today (`messages_api_client.dart:53-67`), so both adapters can be constructed with identical tuning.

On a non-200/network/timeout failure, retries per the existing exact rules (401→`AiAuthException` immediately; 400/403/404/413→`AiInvalidRequestException` immediately; 429→retry up to `maxAttempts` honoring a `retry-after` header (capped at 30s) then `AiRateLimitException`; ≥500→retry then `AiServerException`; a thrown/timed-out `send()`→retry then `AiNetworkException`) — copy this classification logic (`messages_api_client.dart:99-157`, `_retryAfter`, `_maxRetryAfter`) unchanged, since it's already correct and protocol-agnostic (standard HTTP semantics, not Anthropic-specific).
    - A shared, best-effort `String? _extractErrorMessage(String bodyText)` (move `messages_api_client.dart:216-230` here unchanged) — both Anthropic's and OpenAI's error envelopes are `{"error": {"message": "..."}}`, so one implementation correctly serves both.
    - Returning a `Future<Stream<List<int>>>` (not itself being a `Stream`) is deliberate: the retry decision has to fully resolve (reach a 200, or exhaust retries and throw) before there's a byte stream to hand back — this keeps "did the request succeed" and "here are its bytes" as two separate, clearly-sequenced steps, rather than conflating retry control flow with the eventual data stream the way an all-in-one `async*` generator does.

### Architecture constraints

- **AD-9 (I/O isolated to adapters):** `ai_client.dart` stays pure Dart even after gaining `ProtocolRoutingAiClient` — that class does no I/O itself, it only composes two `AiClient`s (which are themselves the ones doing I/O). `ai_transport.dart` uses `package:http` (I/O), same boundary as `messages_api_client.dart` already crosses — both are adapter-support files, not model files.
- **AD-12 (barrel discipline):** `openai_compatible_client.dart` and `ai_transport.dart` are **not** exported from `ai/ai.dart` — only `main.dart` and this slice's own tests import them directly, exactly matching `messages_api_client.dart`'s existing withholding (its own doc comment already states this rule; this story extends it to the two new files by the same reasoning).
- **AD-8 (never blocks, never throws unclassified):** every new failure path in this story routes through the existing `AiClientException` hierarchy — `AiConfigException` for a config that signals an unusable/inconsistent combination (extending Story 4.7's own established pattern for `resolveCustomOrigin`/now `resolveOrigin`), the four HTTP-outcome exceptions for everything transport-level, identically shared between both adapters via `RetryingHttpSender` so there is exactly one place classification logic can drift.
- **Why `AiProtocol` moves but `AiServer` doesn't:** `AiRequest` (the port's own request type, `ai_client.dart`) needs to reference `AiProtocol` directly once routing is per-request (Task 2.2/2.3) — that's a port-level need. `AiServer` has no equivalent port-level consumer; it stays a pure config-parsing concept local to `ai_server_config.dart`. Keep `ai_server_config.dart` importing `AiProtocol` from `ai_client.dart` (not the reverse) — the port must never depend on the config-parsing file (that dependency already exists the other way, for `AiConfigException`).
- **Why the retry/backoff logic is extracted now, not left duplicated:** this codebase's own stated bias is against premature abstraction — but this is not premature: Story 4.8 is the second real, concrete need for the exact same retry/backoff/timeout/status-classification state machine (~80 lines), and leaving it duplicated means every future fix (e.g. Story 4.1's own still-open deferred-work item about in-stream SSE `error` events bypassing retry) has to be applied twice or silently drifts. This mirrors AD-7's own reasoning for the convention matcher ("one matcher, many consumers") applied one layer down the stack.
- **Why `OpenAiCompatibleClient` has no default model but `MessagesApiClient` does:** Anthropic's default (`claude-opus-4-8`) is this app's own opinionated pick for a single, known-good provider. There is no equivalent for "an arbitrary OpenAI-compatible server" — OpenRouter model ids are provider+model-qualified strings the author must choose, and a local server's loaded model is entirely local. Defaulting to *something* here would silently send a request that predictably 404s/400s on a real server; requiring the author to set `ai.model` and failing clearly beforehand (Task 4.4) is the honest behavior, consistent with every other "never silently send to the wrong place" guard this story and Story 4.7 both use.

### Review Findings (Code Review, 2026-08-13)

**Patches Applied (7):**
- [x] [Review][Patch] Dart `Error` vs `Exception` bypass in retry loop [ai_transport.dart:116-122] — `catch (e)` checks `if (e is AiClientException) rethrow;` but not `if (e is Error)`. A `NoSuchMethodError` or `StackOverflowError` from `buildRequest()` would be caught, wrapped as `AiNetworkException`, retried 3 times, then thrown (unlikely but possible edge case). Fixed: `if (e is AiClientException || e is Error) rethrow;`.
- [x] [Review][Patch] Unbounded error response body in retry loop [ai_transport.dart:134] — `response.stream.bytesToString()` reads entire error response with no size limit. A multi-GB error body causes memory exhaustion, especially across retries. Fixed: capped at 1MB via `.take(_maxErrorBodySize)` on the byte stream before decoding.
- [x] [Review][Patch] Integer overflow in `retry-after` header parsing [ai_transport.dart:171-174] — `int.tryParse()` accepts astronomically large numbers; `Duration(seconds: X)` may overflow. Fixed: bounds check added, `seconds > 3600` now returns null (falls back to default backoff).
- [x] [Review][Patch] Empty `choices` array silently skipped [openai_compatible_client.dart:594-595] — Server responds `200` with `{"choices": []}`. Code skips frame, allowing stream to continue. Fixed: now throws `AiServerException('Provider returned empty choices array — no text to stream.')`.
- [x] [Review][Patch] Whitespace-only API keys bypass Bearer check [openai_compatible_client.dart:87] — `apiKey.isNotEmpty` passes for `"   "`. Sends `Authorization: Bearer    ` instead of omitting header. Fixed: changed to `apiKey.trim().isNotEmpty`.
- [x] [Review][Patch] Empty `userContent` silently sent [openai_compatible_client.dart:530] — No validation that user content is non-empty. Empty requests may hang or return garbage. Fixed: guard added in `_buildRequest`, throws `AiConfigException`.
- [x] [Review][Patch] Empty `system` prompt silently sent [openai_compatible_client.dart:529] — Same as above for system prompt. Fixed: guard added, throws `AiConfigException`.
- [x] [Review][Patch] Malformed error response loses context [openai_compatible_client.dart:186-190] — `{"error": {"message": null}}` or `{"error": {}}` fell back to generic "Provider error." with no type details. Fixed: fallback message now includes the error `type` when available (`'Provider error (type: $type).'`).
