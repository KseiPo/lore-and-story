# Story 4.3: Translate RU → EN (release checkpoint)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the author,
I want AI to draft the EN translation of an RU file,
so that I can fill missing translations fast.

## Context

**FR21, and the epics.md ACs for this story:**
> For an RU file lacking its EN pair, the app **generates an English translation** into the EN tab (a create, not an edit), using a context pack of: the RU file + an **alias glossary** (title + RU/EN aliases across entities) + the `ARCHITECTURE.md` §3.3 prose conventions. The author edits the result and saves explicitly.
>
> Given an RU file lacking its EN pair, When I request translation, Then the app assembles the context pack (RU file + alias glossary + prose conventions), shows the FR22 preview, and on confirm streams a translation (via the Story 4.1 client) into the EN tab as a create. Given the draft arrives, When I review it, Then I can edit it and explicitly save to `.en.md`.
>
> **Release checkpoint: this story is independently shippable; grammar (Story 4.4) is not required for it.**

**This is the first story that actually calls the AI.** Story 4.1 built the port + adapter with zero callers ("stand up the plumbing, not wire it into a feature"). Story 4.2 built the confirm/cancel gate, also with zero callers. Neither wired an `AiClient` into the running app — `main.dart` today constructs a `KeyStore` but no `MessagesApiClient`, and nothing downstream of `HomePage` receives an `AiClient` at all. This story is where all three pieces (client, gate, and a real feature) meet for the first time.

**Where the translate action attaches — the existing Story 2.9 synthetic EN tab.** `PairedEditorPage` (`apps/mobile/lib/app/paired_editor_page.dart:71-93`) already detects "a lone `.ru.md` with no `.en.md`" and adds a synthetic EN tab (`_Variant(createIfMissing: true)`) that opens empty and creates the file on first save. That tab already carries a small translate-icon hint next to its label (line 257) — this story adds the actual AI action behind it. **FR21 is RU→EN only** — `PairedEditorPage` also builds a *mirrored* synthetic RU tab for an EN-original file with no RU pair (lines 97-117, Story 2.18's flow); that direction is explicitly **not** in scope here — no Translate action appears there.

**Design decision 1 — where the translate logic lives.** `epics.md`'s slice-ownership table (quoted verbatim in Story 4.2's own Context) names `ai/` as owning "`AiClient` port + Messages-API/SSE adapter + secure key store + context-preview / translate / grammar UI" — translate UI is explicitly `ai/`'s to own, the same reasoning Story 4.2 used to place `context_preview.dart` there instead of `app/`. So the context-pack assembly + confirm/send orchestration is a new top-level function in a new file, `apps/mobile/lib/ai/translate_action.dart`, mirroring `context_preview.dart`'s and `lint_panel.dart`'s shape (a function taking `BuildContext` + collaborators, doing its own `showContextPreview`/dialog work, returning a result) — `paired_editor_page.dart` calls it exactly the way it already calls `runLintAndShowPanel` for the existing Lint action.

**Design decision 2 — the context pack is 4 sections, not 3, closing a Story 4.2 deferred finding.** FR22's wording ("the file, the glossary terms, the conventions") describes 3 sections, but the actual `AiRequest.system` this story builds also needs a short fixed instruction preamble (what to translate, how to treat markup) that isn't any of those 3 things. Story 4.2's own deferred-work.md entry called this out in advance: *"`ContextSection` … cannot structurally represent the full wire payload … include a section for the non-file/glossary/convention parts of the request too."* This story closes that gap directly instead of carrying it forward again: the preview shows **4** sections — `AI instructions`, `The file`, `Glossary terms`, `Conventions` — so every byte of `AiRequest.system` + `AiRequest.userContent` is represented by exactly one section, and "exactly what leaves the device" (AD-11) is literally true, not approximately true.

**Design decision 3 — the RU "file" sent is the tab's live buffer, not a fresh disk read.** `FileEditorState.text` already exists and is documented as "the live, possibly-unsaved content … used by the Story 3.1 linter, which must lint what the author is actually looking at" (`apps/mobile/lib/app/file_editor.dart:137-140`). Translation reuses that exact precedent: if the RU tab has unsaved edits, those are what gets translated (and what the context preview shows) — no forced save first, no silent divergence between "what you're looking at" and "what gets sent."

**Design decision 4 — the glossary is reloaded fresh on each Translate tap, not cached.** `LoreEntry.aliases` is already documented as "Doubles as the AI translation glossary in Epic 4" (`apps/mobile/lib/lore/lore_model.dart:72-74`) — one line per entity, title first then every RU/EN alias, built by `lore.loadLore(storage, loreDir)`. Story 3.1's Lint action already established the precedent of reloading fresh per occasional action rather than caching ("a different tradeoff for a different, occasional action" — `paired_editor_page.dart:197-201`); Translate follows the same reasoning: it fires rarely (once per missing translation), so a fresh, always-current glossary is worth an extra walk. No filtering by relevance to the current file — the full glossary is sent every time, matching MOBILE.md §6.2's estimate ("~2K tokens… cost is a non-issue") literally.

**Design decision 5 — the conventions text is a new hardcoded constant, not read from a doc at runtime.** No AI-ready prose string for ARCHITECTURE.md §3.3 exists anywhere in the app today — `convention_matcher.dart` is a regex/token matcher, not natural-language prose, and ARCHITECTURE.md itself doesn't ship inside the app bundle. A new private constant in `translate_action.dart` transcribes the operative rules from ARCHITECTURE.md §3.3 (dialogue format, inner monologue, placeholders, choice/return link forms, em-dash conditionals — see References below for the exact source section). Kept private/inline rather than hoisted into a shared module now — YAGNI (Story 4.2's own precedent): if Story 4.4 (grammar) turns out to need the identical text, extracting it then is a one-line change.

**Design decision 6 — the stream is buffered, not shown typing live.** `AiClient.sendMessage` returns `Stream<String>`, but this story awaits it to completion (joining every delta) before writing anything into the EN buffer once, rather than appending deltas live as they arrive. Reasoning: live-appending would have to define what happens if the author edits the buffer while a translation is still streaming in (a real race with no clean answer), and a full scene translation is genuinely long output (MOBILE.md §6.4) — a loading spinner for that duration is normal UX, not a regression. This mirrors the existing Lint action's own in-flight spinner pattern (`_linting` bool + `CircularProgressIndicator` swapped in for the icon, `paired_editor_page.dart:285-292`) — Translate gets a `_translating` bool built the same way.

**Design decision 7 — threading `AiClient` through the whole navigation chain, matching the existing `RepoStorage`/`loreDir` pattern exactly.** Nothing between `main.dart` and `PairedEditorPage` carries an `AiClient` today. `RepoStorage`/`loreDir` already thread through this **exact same chain** — `main.dart → LoreStoryApp → HomePage → CategoryEntitiesPage → (navigateToEntity) → EntityDetailPage → PairedEditorPage`, plus every sibling reachable via wikilink-tap-navigation (`EditorPage`, `UndeterminedLanguagePage`, `ConflictsPage`) — so `AiClient` is threaded the identical way: a new required constructor field on every widget in the chain, passed through every call site. This is mechanical, not a new pattern (Task 1 gives the exhaustive file-by-file list). Because every one of these fields is `required`, a missed call site is a **compile error**, not a silent bug — `flutter analyze` is the proof no site was missed (AC9).

**Non-goals (explicitly out of scope):** canceling an in-flight translate request once confirmed; translating EN→RU (the mirrored Story 2.18 tab); any batch/desktop translation path; caching or reusing a previous translation; a diff/merge UI (the EN file doesn't exist yet — this is a create, same as Story 2.9); changing anything about how the EN tab is *saved* (Story 2.9's create-on-first-save path is reused completely unchanged); tuning/iterating on the actual translation-quality prompt wording beyond a reasonable first version (the prompt can be refined later without any contract change, since `ContextSection`/`AiRequest` are already decoupled per Story 4.2's AC6).

## Acceptance Criteria

1. **(FR21 — the action itself)** Given the `PairedEditorPage` synthetic RU→EN tab (a lone RU file with no EN pair) is active and its buffer is non-empty, when the author taps Translate, then the app assembles a 4-section context pack (`AI instructions`, `The file` = the RU tab's live buffer, `Glossary terms` = every entity's `aliases` joined, `Conventions` = the hardcoded prose-conventions text) and shows Story 4.2's `showContextPreview` before anything is sent.
2. **(Gate honored)** Given the context preview is showing, when I cancel it (Cancel, back gesture, or tap-outside — any of Story 4.2's dismissal paths), then no network call happens at all and the EN tab's buffer is unchanged.
3. **(Confirm → stream → populate, not written to disk)** Given I confirm the preview, when the AI response stream completes, then the EN tab's buffer is populated with the full translated text, switched into edit mode, and marked dirty (`FileEditorState.isDirty == true`) — nothing is written to disk by this action; only the buffer changes.
4. **(Explicit save still required, Story 2.9 unchanged)** Given a populated draft, when I review/edit it and tap Save, then the existing create-on-first-save path (`FileEditorState._save` → `RepoStorage.writeAtomic`) creates `.en.md` exactly as it does today for a manually-typed translation — this story does not modify that path.
5. **(Scope — RU→EN only)** Given the mirrored synthetic tab (an EN-original file with no RU pair, Story 2.18's flow), when that tab is active, then no Translate action is shown or reachable — FR21 covers RU→EN only.
6. **(Never corrupt / AD-8)** Given the glossary load or the AI call fails for any reason (a `loadLore` exception, or any `AiClientException` subtype — not configured, auth, invalid request, rate limit, server, network), when the failure happens, then a clear SnackBar message is shown, the EN tab's buffer is left exactly as it was before the attempt, `_translating` clears so the action can be retried, and the app is never stranded.
7. **(Offline-safe by construction — NFR4)** Given the app is used without ever tapping Translate, when any other feature (browsing, editing, saving, linting, the mirrored RU-create-tab, everything from Epics 1–3 and Stories 4.1–4.2) is exercised, then nothing behaves differently from before this story — no new network dependency is introduced anywhere except behind this one explicit action.
8. **(Empty RU guard)** Given the RU tab's live buffer is empty or whitespace-only, when that tab is active, then the Translate action is disabled — there is nothing meaningful to translate.
9. **(Wiring integrity — no missed call site)** Given the new `AiClient` dependency is threaded from `main.dart` down to `PairedEditorPage`, when every existing call site across the navigation chain (`main.dart`, `app.dart`, `home_page.dart`, `category_entities_page.dart`, `entity_navigation.dart`, `entity_detail_page.dart`, `editor_page.dart`, `undetermined_language_page.dart`, `conflicts_page.dart`, and every test that constructs one of these widgets) is updated, then `flutter analyze` is clean and the full `flutter test` suite passes — proof no call site was missed (a missed one is a compile error, not a silent gap).

**Non-goals:** see the Context section's "Non-goals" paragraph above — not repeated here.

### Review Findings

Cross-model adversarial review (Blind Hunter + Edge Case Hunter + Acceptance Auditor, all on Opus; implementation was on Sonnet 5) against the uncommitted diff. Every finding below was verified by reading the actual source directly (not the diff hunk alone) — several were cross-confirmed by two or three review layers independently.

- [x] [Review][Patch] **The system prompt actually sent contains "glue text" that appears in no preview section — the story's own AD-11 verification instruction was not followed.** `runTranslate` builds `AiRequest.system` as `'$_kInstructions\n\nProse conventions to preserve:\n$_kConventions\n\nGlossary — name variants (keep every mention of an entity consistent with one of its listed forms):\n$glossaryText'` — the two label phrases ("Prose conventions to preserve:", "Glossary — name variants...") are directives to the model that never appear in any of the 4 previewed `ContextSection`s. Confirmed independently by all three review layers; this is exactly the class of bug the story's own Dev Notes said to verify byte-for-byte and that verification was never actually done. The existing test only asserts `contains(...)` substrings, which passes despite the gap. [apps/mobile/lib/ai/translate_action.dart:75-78]
- [x] [Review][Patch] **An empty glossary (a project with zero other lore entities) is silently sent as a blank section, and Confirm is never disabled for it.** `loadLore` never throws for an empty/missing directory (`lore_loader.dart:113-114`, "degrades to empty (AD-8)"), so the realistic failure mode isn't the `catch` block — it's `glossaryText == ''` sailing straight through, since `showContextPreview` only disables Confirm when the whole `sections` list is empty, never for an individual section's empty text (`context_preview.dart:88`). FR21 names the glossary as a required part of the context pack; nothing here detects or honestly represents its absence. Every existing Translate test in `paired_editor_page_test.dart` runs against `translationStorage()`, which seeds no `dirEntries` — so all of them exercise this exact empty-glossary path without asserting on it. [apps/mobile/lib/ai/translate_action.dart:52-55]

### Architecture constraints

- **AD-11 (this story is the first real exercise of it):** *"Nothing is sent until the user confirms a context-preview showing exactly what leaves the device."* Design decision 2 above (4 sections, not 3) is what makes this literally true here — verify during implementation that the 4 sections' concatenated text is byte-for-byte what ends up in `AiRequest.system`/`userContent` (a mismatch between what's previewed and what's sent would be a direct AD-11 violation, the exact failure class Story 4.2's own review hunted for).
- **AD-8 (total, never throw, never strand):** every async boundary this story adds (`lore.loadLore`, `aiClient.sendMessage`) must be guarded; a failure must leave the EN tab exactly as it was and clear `_translating` so retry is possible — never a half-populated buffer, never a stuck spinner.
- **AD-9 (purity scope):** `ai/translate_action.dart` is UI (uses `BuildContext`, calls `showContextPreview`), not the pure port — this is expected and matches `context_preview.dart`'s own precedent; AD-9's "no Flutter imports" rule binds only `ai_client.dart`.
- **AD-12 (barrel-only cross-slice access):** `translate_action.dart` must be exported from `ai/ai.dart`'s barrel (like `context_preview.dart` was in Story 4.2); `messages_api_client.dart` stays **not** exported (only `main.dart` and its own test may import it directly) — Task 1.1 imports it directly in `main.dart`, exactly like Story 4.1 already established for `AllFilesRepoStorage`.
- **NFR4/NFR5 (offline-first, nothing sent without the gate):** AC7 exists specifically to prove this story didn't quietly widen when network calls can happen — the only new network-capable code path is behind the Translate button, gated by the same confirm/cancel Story 4.2 already built and tested.

The wiring-only parts of Task 1 don't need their own new tests beyond "existing tests still pass with a `FakeAiClient` threaded through" — a compile-time-enforced parameter addition is not itself a behavior to test.
