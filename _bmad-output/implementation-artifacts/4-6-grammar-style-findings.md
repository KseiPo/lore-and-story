# Story 4.6: Grammar / style findings

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the author,
I want AI grammar/style feedback as a findings list,
so that I can improve prose while keeping my voice.

## Context

**FR23 (epics.md, Story 4.6) and MOBILE.md §6.3:**

> The app requests a grammar/style review and renders a structured findings list (`line`, `issue`, `suggestion`, `severity`) as a tappable list that jumps to the line — never a rewritten file. The FR22 context preview applies.

**Why findings, not a rewrite (MOBILE.md §6.3):** "a diff UI on a phone is real work; 'check for styling/grammar errors' is a findings request, not a rewrite request; and suggestions preserve the author's voice." This is the same reasoning that made Story 4.3 a create-only translation (no diff UI) — grammar review sidesteps the diff problem the same way.

**This is the second and last AI-1/AI-2 feature (MOBILE.md §6.1 table: "Translation ships before grammar... because it is cheaper to build").** Everything Stories 4.1–4.5 built is reused, not rebuilt:
- `AiClient`/`MessagesApiClient` (Story 4.1) — the same streamed-text transport, unchanged.
- `showContextPreview`/`ContextSection` (Story 4.2) — the same mandatory send-preview.
- `AiPromptConfig`/`resolveAiPromptConfig` (Story 4.4, extended by 4.5) — the same `ai-prompts.md` override scheme, gaining one more heading.
- `runLintAndShowPanel`/`showLintPanel` (Story 3.1, `apps/mobile/lib/app/lint_panel.dart`) — **not the code**, but the exact *interaction pattern* this story's UI must mirror: an AppBar action with a spinner while a re-entrancy guard is set, then a bottom-sheet list where tapping a row dismisses the sheet and calls `FileEditorState.jumpToLine(line)`. Story 3.1's findings are offline/syntax-only (`ConventionKind`-based); this story's findings are AI-produced prose judgments (`issue`/`suggestion`/`severity`) — a genuinely different data shape, so this story adds a **new** finding type and panel rather than extending `LintFinding`/`lint_panel.dart`, but the jump-to-line mechanics and re-entrancy-guard shape are copied deliberately (AD-7 at the *pattern* level, not the *type* level — forcing `LintFinding` to carry AI-only fields like `suggestion`/`severity` would pollute Story 3.1's offline-only type for a second, unrelated caller).

**Deferred-work.md's own forward reference confirms this was anticipated:** Story 4.4's deferred-work entry says `# Translation Instructions` "is deliberately feature-qualified for forward-compatibility with a future `# Grammar Instructions` heading (Story 4.6)" — so extending `ai_prompt_config.dart`'s heading scheme with a `# Grammar Instructions` override is explicitly in scope here, not a scope-creep addition. (FR29 itself is feature-agnostic — "an AI action," not "the translate action" — grammar review not being overridable while translation is would be an inconsistent, half-finished FR29.)

**Unlike Translate, this feature is not RU/EN-direction-specific and not pair-aware.** Any open file — a single-file `EditorPage`, or the active tab of a `PairedEditorPage` — has prose that can be reviewed. So the Review action is added to **both** host pages (mirroring where Lint already lives on both), not just the paired editor (where Translate lives).

## Acceptance Criteria

1. **(Request + structured findings, FR23)** Given a file open in the editor (either `EditorPage` or the active tab of `PairedEditorPage`), when I tap the grammar/style Review action, then — after the FR22 context preview and my confirmation — the app sends the buffer to the AI and renders the result as a findings list, each finding showing its issue, its suggestion, its severity, and the line it applies to.
2. **(Tap-to-jump)** Given a rendered findings list, when I tap a finding, then the panel dismisses, the editor exits preview mode (if it was in it), and the caret jumps to that finding's line — mirroring `FileEditorState.jumpToLine`'s existing Story 3.1 behavior exactly (same method, same effect).
3. **(Never a rewritten file)** Given a completed review, when the findings render, then the editor's buffer is completely untouched — no text is inserted, replaced, or auto-applied anywhere. A suggestion is text to read, not text that gets written into the buffer by this feature.
4. **(FR22 preview, byte-for-byte / AD-11)** Given a Review request, when the context preview opens, then it shows every section that will actually be sent (at minimum an `AI instructions` section and a `The file` section), and the `system`/`user` payload `MessagesApiClient` actually sends is built only by concatenating those same section texts — never a re-derived or additional string (mirroring `runTranslate`'s own AD-11 discipline).
5. **(`ai-prompts.md` override, extends FR29)** Given a file named `ai-prompts.md` at the repo root with a `# Grammar Instructions` section, when I request a review, then that section's text replaces the app's hardcoded grammar instructions in both the preview and the sent request. Given the section is absent, the file is missing/unreadable, or the section's body is empty after trimming, the hardcoded default is used — mirroring Story 4.4's own "empty body → not overridden" rule exactly (`AiPromptConfig`'s existing `flush()` behavior extends to the new field with no new logic branch).
6. **(Empty findings is a real, honest result)** Given a review that completes with no issues found, when the list renders, then it shows a clear "No issues found" state (mirroring `showLintPanel`'s `findings.isEmpty` branch) — distinct from a failure (AC7) and distinct from "review not yet run."
7. **(Never crashes on a malformed response, AD-8)** Given the AI's response is not valid JSON, is valid JSON but not the expected shape (not a list, or a list entry missing a required field), or the request itself fails (network/auth/rate-limit/server error — the existing `AiClientException` hierarchy), when this happens, then the app shows a clear error (a `SnackBar`, mirroring `runTranslate`'s `_showError`) and never throws an uncaught exception or leaves the UI stranded. A response that is valid JSON overall but has some malformed individual entries degrades gracefully — the well-formed entries still render (mirroring `lintText`'s own total, best-effort collection philosophy), rather than discarding the whole result over one bad entry.
8. **(No regression)** Given every existing Story 3.1–4.5 test in `editor_page_test.dart`, `paired_editor_page_test.dart`, `ai_prompt_config_test.dart`, and `translate_action_test.dart`, when this story ships, then they all keep passing unmodified — this story is additive only.

**Non-goals** (explicitly out of scope, matching FR23's letter and MOBILE.md §6.3's own reasoning):
- Auto-applying a suggestion to the buffer, or any diff/accept-reject UI — findings are read-only text (AC3); a future story could add "tap suggestion to insert," but nothing in FR23 asks for it and it reopens exactly the diff-UI problem §6.3 says this feature is designed to avoid.
- A dedicated Conventions-style second override section for grammar (i.e. no `# Grammar Conventions` heading) — unlike translation's fork between `# Translation Instructions` and `# Conventions` (two genuinely different concerns: how to translate vs. what the markup means), grammar review only needs one instructions block, which can describe the project's markup conventions inline (see Task 1). Revisit only if a real need for a second, independently-overridable piece surfaces.
- Any change to `AiClient`/`MessagesApiClient`/`ai_client.dart`'s exception hierarchy or streaming transport — reused completely unchanged, same as Story 4.3/4.5 did.
- Jumping to / highlighting the specific *span* an issue refers to within its line — the line number is enough (matches Story 3.1's own line-level granularity; `jumpToLine` is line-oriented, not offset-oriented).
- A severity-based sort or filter on the findings list — render in the order the AI returned them, same as `showLintPanel` does today (no reordering logic in Story 3.1 either).
- Multi-language-aware phrasing changes to the grammar instructions (unlike Translate, there's no "direction" here) — one instruction set works for whichever language the open file happens to be in; the AI is capable of detecting that itself.

### Architecture constraints

- **AD-8 (total, never throw, never strand):** `runGrammarReview` and its response parser must be unconditionally total. This story's response parsing is a **new failure surface** none of Stories 4.1–4.5 had (they never parsed the AI's output as structured data — translation just streams raw text straight into a buffer) — the top-level-malformed-JSON case and the malformed-individual-entry case are both real, expected inputs to design for, not edge cases to bolt on after.
- **AD-11 (byte-for-byte preview-vs-sent):** exactly as `runTranslate`'s own doc comment describes — build `AiRequest.system` only by concatenating the same `ContextSection.text` values shown in the preview, never a second/re-derived string.
- **AD-7 (extend the shared mechanism, don't fork it):** `ai-prompts.md`'s heading scheme gains a fourth heading via the same `Map<String, _Heading>` + enum-`switch` pattern — not a second parser. The Lint-action *interaction pattern* (AppBar icon + spinner + re-entrancy guard + bottom sheet + tap-to-jump) is mirrored deliberately; the *data type* (`GrammarFinding` vs. `LintFinding`) is deliberately **not** shared — see Context section's reasoning. Getting this distinction backwards (either forking the heading parser, or trying to force AI findings through `LintFinding`) is the single most likely wrong turn in this story.
- **AD-12 (barrel discipline):** `app/` code may only import `ai/ai.dart`, never `ai/grammar_action.dart` directly — export it from the barrel (Task 4.4).
- **Testing standard for this story:** the JSON-parsing logic (Task 2.4) is the highest-risk, least-precedented part of this story — no prior story in this codebase has parsed structured AI output. Write the malformed-JSON and malformed-entry tests *first*, not as an afterthought, since AD-8's "never crash" guarantee is exactly what those tests exist to pin down.

### Previous story intelligence

Story 4.5 (most recently completed, done 2026-08-08) and Story 4.4 are the direct dependencies:
- Story 4.4 established the enum-`switch` field-routing pattern in `ai_prompt_config.dart` specifically so a typo can't silently degrade a heading to "never overridden" — Task 1 extends that same shape for a fourth field; do not introduce a `Map<String,String>`-keyed alternative.

This story's `PairedEditorPage` wiring (Task 4.2) reads only the **active** tab (`_active`, exactly like Lint already does), so this specific gap does not recur here — but it's a reminder that any cross-tab state assumption in this codebase needs empirical verification, not just reading the widget tree and reasoning about it.
- Story 4.5's review round found and fixed a real data-loss bug (AC2's overwrite guard) and a staleness bug (stale in-memory snapshot) — both were caught by re-reading actual current source during implementation, not by trusting the story's own plan text. This story's Task 2.4 (response parsing) is new, unprecedented logic in this codebase — treat its own plan the same way: verify assumptions about model JSON output behavior empirically via tests, don't just trust that the model will always follow the fence-free-JSON instruction (hence Task 2.4's explicit fence-stripping step).
- `deferred-work.md`'s Story 4.3 entry already flags forward: "`AiAuthException`/etc. are all flattened into one generic SnackBar message... worth a 'No key configured — open Settings' shortcut... once a second real caller of this exception-handling shape exists (grammar findings, `4-6-grammar-style-findings`)." Implementing the shortcut is **not** required by any AC here (it wasn't required by 4.3/4.5 either) — leave it as a still-deferred item unless it's essentially free to add while touching this error-handling code; do not silently expand scope.
